# 模块解剖笔记辅助

借助 AI 快速"吃透"项目核心模块，生成结构化笔记，准备面试讲解。

## 核心原则

**AI 读代码 + 用户做决策**。AI 负责扫描代码、提取信息、生成初稿；用户负责判断设计理由、补充真实踩坑经历、打磨面试话术。

| 环节 | AI 负责 | 用户负责 |
|------|---------|--------|
| 代码骨架提取 | 扫描 import、export、函数签名 | 判断哪些是核心 API |
| 关键设计定位 | 标记注释密集处、分支复杂处 | 判断哪些设计决策值得写进笔记 |
| 笔记初稿生成 | 按模板填充前 2 节 | 修改第 3~6 节（设计/坑/重做/面试话术） |
| 盲点检查 | 追问"这个分支失败怎么办" | 确认答案是否真实 |

---

## 两种输出形态

本 Skill 根据用户请求生成两种文档：

| 形态 | 触发语句 | 特点 | 篇幅 |
|---|---|---|---|
| **模块解剖笔记** | "我要吃透 xxx.ts" / "给 xxx 写模块笔记" | 聚焦单个文件，完整覆盖 why/what/how/面试/术语 | 中等（约 5000-10000 字） |
| **阶段学习文档** | "按阶段出学习文档" / "写类似 prompt阶段1 的文档" | 聚焦一个阅读阶段，先主干后细节 | 较长（单阶段约 8000-15000 字） |

两种形态都要遵循下文的质量标准，但阶段文档更强调**前置概念、流程图、例子分层、验收标准**。

## 执行流程

### 第一步：扫描代码骨架（AI 自动执行）

读取目标文件，生成骨架摘要：

1. **关键依赖**：列出 import 的模块（排除类型 import）
2. **导出清单**：列出所有 export 的函数/类/类型，每个一句话说明用途
3. **核心函数**：标记函数体超过 50 行或分支超过 3 个的函数
4. **注释密集段**：列出中文注释密集的代码行号范围和内容摘要

输出格式：

```
## 骨架摘要：[文件名]

### 关键依赖
- [依赖1] — [用途]
- [依赖2] — [用途]

### 导出清单
- [导出1] — [一句话用途]
- [导出2] — [一句话用途]

### 核心函数
- [函数名]（约XX行，含XX分支）— [核心职责]

### 注释密集段
- L120-L145：[注释内容摘要]
- L200-L220：[注释内容摘要]
```

### 第 1.5 步：无注释代码的推断策略（AI 自动执行，按需触发）

**触发条件**：当第一步发现注释密度 < 10%（即大部分函数/代码段没有中文注释）时，启用本策略。注释稀少时 AI 更容易编造设计理由，必须用多种推断法交叉验证，并标注置信度。

**5 种推断法（按可靠性排序，优先用靠前的）**：

| 推断法 | 做法 | 示例 |
|--------|------|------|
| ① 命名推断 | 从函数名、变量名、参数名推断意图 | `stoppedByNoProgress` → 存在"无进展检测"机制；`fcKnowledgeBaseResult` → FC 降级时复用知识库结果 |
| ② 调用方推断 | 用 Grep 搜索该符号的所有引用点，从调用上下文反推用途 | `sessionAssetCache` 被 `saveSessionAssets`/`getSessionAssets` 调用 → 会话级资产缓存 |
| ③ 相邻代码推断 | 看同文件顶部模块注释、相邻函数注释，从模块定位推断当前函数职责 | 文件头注释说"本模块负责 FC 调度"，即使某内部函数无注释，也能定位为调度辅助 |
| ④ Git History 推断 | 执行 `git log -L :函数名:文件路径 --oneline -5` 看 commit message | commit "fix: 防止 tool_choice 死循环" → 解释了为什么维护 `llmWithToolsAuto` |
| ⑤ 测试用例推断 | 查找同目录 `*.spec.ts`，测试用例名说明预期行为 | `it('should fallback to RAG when FC fails')` → 证实降级路径存在 |

**置信度标注规则**（所有推断结论必须标注）：

- 🟢 **高置信度**：命名清晰 + 多处引用一致 + 有测试覆盖 → 可直接写入笔记
- 🟡 **中置信度**：命名可推断但无测试，或 git history 有线索 → 写入笔记但标注"⚠️ 推测"
- 🔴 **低置信度**：命名模糊 + 无引用 + 无测试 + 无 git 线索 → **必须单独列出**，提示用户确认，不得直接写入笔记正文

**输出格式**：

```
## 无注释代码推断报告

### 推断法使用情况
- 命名推断：覆盖 X 个符号
- 调用方推断：Grep 了 Y 个关键符号，命中 Z 处引用
- Git History 推断：检查了 N 个函数的提交历史
- 测试用例推断：找到/未找到对应测试文件

### 推断结论（按置信度分组）

🟢 高置信度（可直接写入笔记）：
- [符号1]：[推断用途] — 依据：[命名 + 引用点]
- [符号2]：[推断用途] — 依据：[测试用例名]

🟡 中置信度（写入笔记但标注推测）：
- [符号3]：[推断用途] — 依据：[git commit message] ⚠️ 推测

🔴 低置信度（必须用户确认，不得写入正文）：
- [符号4]：[推断用途] — 无法确认，请用户补充
- [符号5]：[推断用途] — 无法确认，请用户补充
```

**注意事项**：
- 推断法 ④（Git History）需要执行 shell 命令，若用户未授权可跳过，改用其他 4 种
- 推断法 ⑤（测试用例）用 Glob 搜索 `*.spec.ts` / `*.test.ts`，找不到则跳过
- **禁止**把低置信度推断直接写进第三步的"关键设计"，这些只能放在"低置信度"列表等用户确认

### 第二步：深入核心函数（AI 自动执行）

针对第一步识别的核心函数，提取：

1. **函数签名**：输入参数和返回值
2. **执行流程**：主流程用编号步骤列出，每步一句话
3. **分支矩阵**：所有 if/else 分支的触发条件，用表格输出
4. **降级路径**：所有 try/catch 的 catch 块做了什么
5. **外部调用**：调用了哪些外部依赖（LLM、Redis、SSE 等），调用时机是什么

输出格式：

```
## 核心函数分析：[函数名]

### 签名
[函数签名]

### 执行流程
1. [步骤1]
2. [步骤2]
...

### 分支矩阵
| 条件 | 走向 | 说明 |
|------|------|------|
| [条件1] | [分支A] | [说明] |

### 降级路径
| 异常点 | catch 行为 | 用户感知 |
|--------|-----------|---------|
| [异常1] | [降级动作] | [是否感知] |
```

### 第三步：生成笔记初稿（AI 自动执行）

基于前两步的分析，按以下模板填充前 3 节：

```markdown
# 模块名：[文件名]

## 1. 一句话定位（why）
[不超过 50 字，说清解决了什么问题]

## 2. 核心 API（what）
- [API 1] — [一句话说明]
- [API 2] — [一句话说明]
（只列 3~5 个最重要的）

## 3. 关键设计（how）
1. **[设计决策1]**：为什么用 X 而不用 Y — [理由]
2. **[设计决策2]**：为什么用 X 而不用 Y — [理由]
3. **[设计决策3]**：为什么用 X 而不用 Y — [理由]
（列 3 个非显而易见的设计决策）
```

**注意**：第 3 节的"为什么"AI 只能基于代码推测，必须提示用户确认真实原因。

### 第四步：面试官追问（AI 自动执行）

笔记初稿生成后，扮演资深技术面试官，针对该模块提出 5 个追问：

- 2 个针对边界情况（异常、并发、失败）
- 2 个针对设计取舍（为什么不用 X 方案）
- 1 个针对可扩展性（如果要加新功能怎么改）

每个问题附上"参考答案要点"，但单独放在折叠区域，供用户自测后再查看。

输出格式：

```
## 面试官追问（请先自测，再看参考答案）

### 问题 1（边界）：[问题]
<details><summary>参考答案要点</summary>
[答案要点]
</details>

### 问题 2（边界）：[问题]
...
### 问题 3（取舍）：[问题]
...
### 问题 4（取舍）：[问题]
...
### 问题 5（扩展）：[问题]
...
```

### 第五步：对照文档查漏补缺（AI 自动执行）

读取 `项目技术架构与分析文档.md` 中该模块对应章节，与笔记初稿对比：

1. **文档有但笔记没提到的设计决策**（列出条目）
2. **笔记有但文档没提到的点**（标记为"用户独特理解，保留"）
3. **两者描述不一致的地方**（提示用户去代码确认）

> 目标文件：[xxx.ts](file:///...)
> 测试文件：[xxx.spec.ts](file:///...)
> 所属项目：...
> 建议阅读时长：xx 分钟

## 0. 本文档是做什么的？
### 0.1 一句话说明
### 0.2 为什么这个文件值得单独吃透？
### 0.3 适合谁读？
### 0.4 读完本文档，你能回答这些问题

## 1. 读代码前你必须知道的 N 件事
- 每个概念按：代码位置 → 专业解释 → 大白话翻译 → 一句话记住
- 必须有表格/代码片段辅助

## 2. 文件整体结构速览
- 区域/行号/内容表格
- 关键依赖说明
- 导出清单（含调用方）

## 3. 逐段精读
- 每段结构固定为：
  1. 代码位置（file:/// 可点击链接）

## 4. 事件/变量/类型总表（如适用）

## 6. 验收标准

- 每个问题附参考答案

## 7. 你可以用这段话自测
- 要求用户不看代码复述一段话

## 9. 面试官追问

## 10. 与架构文档对照

## 11. 需要你补充的部分（AI 填不了）
- 踩过的坑 / 如果重做 / 面试一句话

## 12. 学习路径建议

## 13. 术语表
```

## 生成阶段学习文档规则（最佳实践）

当用户要求"按阶段出学习文档"或"写类似 prompt阶段1 / prompt阶段2+3 的文档"时，应遵循以下输出规范：

### 1. 文档定位

每份文档**只聚焦一个阶段**（如阶段一、阶段二+三），不追求一次性覆盖全部。阶段划分原则：

- **阶段一**：建立主干——只抓"输入 → 输出"主流程，先忽略防御/优化细节
- **阶段二**：核心机制——工具调用循环、熔断、降级、状态管理等次主干
- **阶段三**：防御与细节——嘴炮防线、过滤、限流、边界兜底等
- **阶段四/五**：旁支系统——缓存、资产、流式过滤等（按需继续分）

### 2. 单文档结构（强制顺序）

```markdown
# 阶段 X 详细讲解

## 0. 先建立一个总认知（大白话 + 专业版）
> 解决"为什么要先看这些"的问题，200 字以内，用一句话概括本阶段核心。
> 可以用类比帮助理解：阶段一 = 会开车；阶段二 = 车坏了知道走备用路线；阶段三 = 司机嘴上说要刹车但没刹，系统能识别并纠正。

## 1. 读代码前先搞懂 N 个概念
> 每个概念按：代码位置 → 专业解释 → 大白话翻译 → 一句话记住。
> 必须有表格/代码片段辅助。
> 对于关键变量，列出：变量名 | 位置 | 类型 | 作用 | 谁生产 | 谁消费

## 2. 阶段 X 完整数据流/流程图
> 用文本流程图或表格展示本阶段数据/控制流向。

## 3-N. 分段讲解（按代码行号顺序切分）
> 每一段聚焦一个代码区域，结构固定为：
> 1. 代码位置（file:/// 可点击链接）
> 2. 这段代码做什么（一句话）
> 3. 关键变量/分支解释
> 4. 举例（具体场景 + 输入输出 + 大白话解释）
> 5. 一句话记住

## 阶段 X 你要画出的图
> 强制要求用户手绘一张图：数据流图 / 状态机 / 时序图。

## 阶段 X 验收标准
> 读完阶段 X，你至少要能回答这 N 个问题。
> 每个问题附参考答案（放在代码块里）。

## 你可以用这段话自测
> 要求用户不看代码复述一段话，判断是否合格。

## 面试可能的追问
> 5 个左右，含边界 / 取舍 / 扩展三类，答案放在 <details> 折叠区。

## 阶段 X 暂时不要深究的内容
> 明确告诉用户哪些内容属于下一阶段，避免在主线没建立时跳读。
```

### 3. 举例要求（强制）

每个核心概念/分支必须配至少一个例子，例子分四层：

```markdown
### 举例：XXX

场景描述：
```text
用户说"帮我生成一张猫的图片"
```

代码层面的输入：
```typescript
const promptText = '帮我生成一张猫的图片';
const intentDetection = detectToolIntent(promptText);
```

代码层面的输出：
```text
intentDetection = {
  shouldForce: true,
  specificTool: 'generate_image'
}
```

大白话解释：
```text
系统识别到用户要生成图片，于是准备锁定 generate_image 工具，
不让模型用文字糊弄过去。
```
```

**禁止只给抽象解释不给例子**。例子必须具体到：输入字符串、函数返回值、模型行为、用户感知。

### 4. 行号引用格式

所有代码位置必须使用 file:/// 协议的可点击链接：

```markdown
位置：[promptTemplate 主入口](file:///e:/miaoma-ai-app/servers/jerry-llm-server/src/fundamentals/prompt.ts#L2396-L2450)
```

- 短函数：精确到函数首尾行
- 长分支：精确到关键 if/else 行
- 变量定义：精确到声明行

### 5. 大白话与专业对照

每个复杂设计必须同时提供两种表述：

```markdown
**专业版**：`resolveModelCapabilities` 合并静态默认值与探测覆盖值，探测优先，
但 `supportsToolChoice === false` 不可被覆盖。

**大白话版**：车管所（阶段1）有本户口本（AVAILABLE_MODELS），还有份体检报告（capabilities.json）。
 normally 听体检报告的；但如果户口本上盖了"终身禁驾"红章（supportsToolChoice=false），
 体检报告说你身体再好也不算数。
```

### 6. 阶段之间如何关联

如果用户要求"阶段 1+2+3 的联系"，新建独立文档 `xxx联系关系.md`，结构如下：

```markdown
# 三个阶段的联系关系

## 1. 物理位置关系（代码行号图）
## 2. 大白话总比喻（贯穿三个阶段的统一类比）
## 3. 一个真实场景串讲（时间轴 T0-TN）
## 4. 跨阶段变量血脉表（谁生产、谁消费）
## 5. 输入输出契约表
## 6. 专业 vs 大白话对照速查表
## 7. 三句话总结
## 8. 自测追问
```

### 7. 验收标准格式（强制）

每个阶段文档必须包含验收标准，格式如下：

```markdown
## 阶段 X 验收标准

读完阶段 X，你至少要能回答这 N 个问题。

### 问题 1：[主干问题]

参考答案：

```text
[完整答案，放在代码块里]
```

### 问题 2：[主干问题]
...
```

**合格标准**：能不看代码回答所有主干问题。
**优秀标准**：能讲清问题之间的关系、能举出具体代码位置、能说出设计取舍。

### 8. 自测段落格式（强制）

每个阶段文档必须包含自测段落：

```markdown
## 你可以用这段话自测

读完阶段 X 后，你应该能不看代码，说出下面这段话：

> [一段 200-400 字的总结性文字，覆盖本阶段核心链路]

如果你能用自己的话讲出这段话，阶段 X 就算合格。
```

### 9. 暂时不要深究的内容（强制）

每个阶段文档必须明确告知边界：

```markdown
## 阶段 X 暂时不要深究的内容

如果你现在还回答不了下面这些，不用急，它们属于后续阶段或更深入优化：

| 问题 | 建议放到哪里看 |
|---|---|
| [问题1] | [下一阶段/另一个文件] |
| [问题2] | [重构思考/面试追问] |

阶段 X 的核心不是 [旁支细节]，而是 [主干问题]。
先把 [主干] 讲清楚，就已经很有含金量了。
```

### 10. 质量控制检查清单

文档生成后，按以下清单自检：

- [ ] 每个阶段是否有"0. 总认知"段落？
- [ ] 每个核心概念是否有"一句话记住"？
- [ ] 每个核心分支是否有具体例子（场景 + 输入 + 输出 + 大白话）？
- [ ] 是否有"你要画出的图"？
- [ ] 是否有"验收标准"（含参考答案）？
- [ ] 是否有"自测段落"？
- [ ] 是否有"暂时不要深究的内容"？
- [ ] 面试追问是否覆盖边界、取舍、扩展三类？
- [ ] 所有代码位置是否可点击？
- [ ] 是否标注了哪些结论是 AI 推测需用户确认？

### 11. 与用户互动的节奏

- 每生成一个阶段文档后，**不要一次性生成全部阶段**，给用户消化空间。
- 用户说"继续"或"下一阶段"再生成下一个。
- 用户要求"直接出文档"时，先确认分几个阶段、目标读者水平，再按规则生成。

## 笔记模板（完整版）

用户最终需要完成的完整笔记模板：

```markdown
# 模块名：[文件名]

## 1. 一句话定位（why）
这个模块解决了什么问题？

## 2. 核心 API（what）
对外暴露 3~5 个函数/类，每个一句话说明

## 3. 关键设计（how）
3 个非显而易见的决策（"为什么这样写"而不是"做了什么"）
⚠️ AI 生成的理由需用户确认真实性

## 4. 踩过的坑（learn）
我曾经的错误版本是什么？为什么改？
⚠️ AI 无法填写，必须用户自己补充

## 5. 如果重做（grow）
现在让我重写，会怎么改？

## 6. 面试一句话
被问到时，30 秒内的最强表述是？
```

## AI 的三个陷阱（必须提醒用户）

1. **AI 会编造设计理由** — 它会说"这样做是为了性能优化"，但实际原因可能只是"当时赶工随手写的"。第 3 节的"为什么"必须用户自己确认。

2. **AI 不了解真实踩坑经历** — 第 4 节"踩过的坑"AI 填不了，这恰恰是面试时最有说服力的部分。比如"TypeORM synchronize 差点丢数据"这种故事，只有用户自己知道。

3. **无注释时 AI 更容易编造** — 代码没有注释时，AI 失去了一个重要的"设计意图来源"，会倾向于用"看起来合理"的理由填充（如"为了性能优化"）。第 1.5 步的置信度标注就是为了对抗这个倾向：低置信度推断**必须**单独列出等用户确认，不得直接写进笔记正文。如果用户确认不了，宁可留空也不要编造。

## 使用方式

用户说以下任一语句时触发本 Skill：

- "帮我解剖 xxx 模块"
- "我要吃透 xxx.ts"
- "给 xxx 写模块笔记"
- "我要准备 xxx 模块的面试讲解"
- "模块解剖"

执行时：
1. 确认目标文件路径（如果用户只说了模块名，先搜索定位文件）
2. 按第一步→第五步顺序执行（注释稀少时在第 1.5 步触发推断策略）
3. 每步完成后简要展示结果，等用户确认后再继续下一步
4. 最终提醒用户补充第 4~6 节（AI 无法生成的部分）
5. 若第 1.5 步产生了🔴低置信度项，在最终输出时再次列出，提醒用户逐条确认或留空

## 用户自定义规则（从本项目 prompt 阶段文档抽象）

本项目用户偏好以下风格的模块学习文档：

1. **先主干后细节**：阶段一只看主流程，不引入三道防线/过滤/缓存等旁支。
2. **每个变量都要追代码位置**：不只讲概念，必须带 `[变量名](file:///...)` 链接。
3. **验收标准附参考答案**：每个问题必须有完整参考答案，方便自测。
4. **必须有自测段落**：要求用户合上书复述一段话。
5. **专业 + 大白话双版本**：复杂设计必须同时给两种解释，优先用生活化类比。
6. **持续补例子**：用户对抽象概念理解有困难时，立刻补具体场景例子（场景 + 输入 + 输出 + 大白话）。
7. **联系文档单独成篇**：学完多个阶段后，必须有一个把它们串起来的独立文档。
