# 用户记忆向量检索改造实施方案

> 状态：待评审
> 日期：2026-10-12
> 关联：`REDIS_INFRASTRUCTURE.md`（可选组件降级思想的同款复用）、`memory.service.ts`、`memory-extractor.ts`、`fundamentals/vector-store/`

---

## 1. 背景与问题

### 1.1 事故还原

用户记忆条数超过 20 条后，"QQ 邮箱"这条记忆排在第 21 位，AI 无法召回——用户要求"发送到我的邮箱"时 AI 只记得飞书、不记得邮箱。

### 1.2 根因

当前注入链路（`memory.service.ts` → `getMemoriesForInjection`）按 **importance DESC + updatedAt DESC 排序后硬编码取前 20 条**注入 System Prompt，与用户当前提问内容**完全无关**。记忆表本身无总量上限，随使用持续累积，top-20 截断问题必然反复发生。

### 1.3 现状盘点（可复用的基础设施）

| 需要 | 已有 |
|---|---|
| 向量数据库 | ChromaDB（知识库在用，`fundamentals/vector-store/`） |
| Embedding 模型 | bge-m3（siliconflow） |
| 混合检索经验 | `multi-hop-search.ts`（BM25 + 向量） |
| 可选组件降级先例 | Redis（`REDIS_ENABLED=false` 自动降级）、输出自检 fail-open |
| 记忆 CRUD 与提取 | `memory.service.ts`（含 merge 合并）、`memory-extractor.ts`（每 10 条消息提取一次） |
| 前端记忆模块 | 记忆与摘要页面（已有增删改 UI） |

**结论：改造成本低，不引入新依赖，不动表结构。**

---

## 2. 目标与非目标

### 目标

1. 记忆条数不设上限的前提下，与当前问题相关的记忆总能被召回（根治 top-20 截断）；
2. 核心信息（importance=5，如联系方式、身份）永不失忆；
3. 向量库任何故障下，系统自动降级回现有 top-20 行为——**任何时刻效果都不差于现状**；
4. 用户自定义记忆的增删改实时同步到向量库（写穿），且同步状态对用户可见、可手动修复；
5. 多用户隔离：用户 A 的记忆绝不漏进用户 B 的上下文。

### 非目标

- 不做记忆衰减/过期机制（记忆库上规模后再立项）；
- 不上 rerank 精排（当前规模收益不明显）；
- 不改动记忆提取触发策略（每 10 条消息提取一次维持不变）。

## 3. 总体架构

### 3.1 核心原则

> **MySQL 是唯一的真相源，向量库只是派生的检索目录。** 目录可以脏、可以丢，任何时候都能从账本（MySQL）全量重抄一份。

与项目既有原则一致："Redis 不是数据真相源"。向量库同理——它是索引，不是存储。

### 3.2 架构图（文字版）

```
┌────────────────────────────────────────────────────────┐
│ 写路径（CRUD + 自动提取）                                │
│   任何写入 → MySQL 落库（真相） → 写穿同步到向量库          │
│   同步失败：不回滚，记"待同步"标记 + error 日志            │
├────────────────────────────────────────────────────────┤
│ 读路径（每轮对话注入）—— 三级瀑布                         │
│   ① 核心层：importance=5，直查 MySQL，永远注入（≤10 条）  │
│   ② 检索层：向量检索 top-K（query=当前消息+最近2轮）       │
│   ③ 兜底层：MySQL LIKE 关键词命中 + top-20 兜底           │
│   三路合并去重（按记忆 id）→ Token 预算内注入              │
│   ② 失败/超时 → 自动落到 ③，warn 日志告警                 │
├────────────────────────────────────────────────────────┤
│ 自愈路径                                                 │
│   全量重建 = 存量迁移工具 = 自愈手段（一个动作三种用途）    │
└────────────────────────────────────────────────────────┘
```

## 4. 存储层设计

### 4.1 独立 Collection（硬隔离）

新建 ChromaDB collection：`user_memories`，与知识库文档 collection 物理分离。

**为什么不用同 collection + metadata 过滤**：记忆与知识库是生命周期完全不同的数据——记忆几百条、增删频繁、按用户隔离；知识库几万块、只增不改、按文档组织。混放后过滤条件写错一个字段就是事故（AI 把知识库片段当"用户说的"引用）。分抽屉成本≈0，收益是隔离的确定性。

### 4.2 文档模型（一条记忆 = 一个 chunk）

记忆都是短文本（远小于 embedding 上限），**不做切分，一条记忆 = 一个向量文档**：

```
id:          mem_{memoryId}        # 确定性 ID，MySQL 主键直拼（同步的钥匙）
document:    记忆正文
metadata:
  userId:      'xxx'               # 每次检索强制过滤（多用户安全底线）
  memoryId:    123                 # 回指 MySQL 主键
  importance:  5
  category:    'fact'
  updatedAt:   '2026-10-12T...'    # 供对账与调试
```

### 4.3 三层隔离总结

| 层 | 手段 | 防什么 |
|---|---|---|
| Collection 级 | `user_memories` 独立抽屉 | 记忆与知识库混淆 |
| metadata 级 | userId 强制过滤 | 用户 A/B 记忆串扰 |
| ID 级 | `mem_{id}` 回指 MySQL | 增删改精确同步（搜索式删除是模糊的，ID 删除是精确的） |

### 4.4 编辑同步规则：改内容与改属性分两档

用户可编辑记忆的内容与属性（类别 fact/decision/preference/context/skill、重要性），两档同步动作：

| 用户编辑了什么 | MySQL | 向量库动作 | 原理 |
|---|---|---|---|
| **内容**（如邮箱地址本身） | 更新正文 | 重新 embed，同 ID 覆盖 | 内容变 = "意思"变 = 指纹必须重算 |
| **属性**（类别改挂、调星级） | 更新字段 | 仅按 ID 更新 metadata，**不重新 embed** | 内容没动，"意思"没变，向量不用重算 |

属性编辑因此是零 embedding 成本的毫秒级操作。类别/重要性变更必须写穿——否则 UI 显示与检索过滤用的 metadata 漂移。

### 4.5 类别治理：不分子类，受控扩展

**① 不按类别分子 collection（明确否决）**

检索靠"意思"找、不靠"标签"找。用户问"发到我的邮箱"时，系统无法预知该记忆被标成"事实"还是"上下文"——分抽屉就必须先猜对抽屉，猜错 = 直接漏召回；且 LLM 打标本身有主观性，类别标错常见，分抽屉会把打标错误放大成检索事故。

类别的正确用途：**UI 展示 + 可选过滤**（记忆页按类别筛选列表、"只在偏好类里找"类高级场景），不参与主检索链路。metadata 留 `category` 字段即够。

**② 新类别：提议 + 归一化守护（受控扩展）**

完全放开 LLM 自由命名会导致"分类法污染"（"偏好"/"preference"/"preference2" 并存，过滤与统计失真）；死守 5 个固定类别则会逼 LLM 硬塞不合适的记忆。折中方案：

1. 提取（memory-extractor）或用户编辑时，LLM/用户可在内置 5 类都不合适时**提议**新类别；
2. 服务端**守护**：trim、统一格式、同义词归并（"偏好"→preference 类映射）、与现有类别语义相似度去重——相似度够高归入现有类，不新建；
3. 通过守护的新类别才生效；UI 下拉读 `SELECT DISTINCT category` 动态渲染，**表结构不动**（category 本为字符串列）。

## 5. 注入链路：三级瀑布

### 5.1 三层角色

| 层 | 来源 | 数量 | 职责 | 失效模式 |
|---|---|---|---|---|
| ① 核心层 | MySQL 直查 importance=5 | ≤10 | 关键信息永不失忆（保险丝） | 只依赖 MySQL，与向量库零耦合 |
| ② 检索层 | 向量检索 | top-8 | 长尾记忆按需想起 | 失败→落③ |
| ③ 兜底层 | MySQL LIKE 关键词 + importance+时间 top-20 | ≤20 | 系统整体不倒 | 现状行为，永远可用 |

**为什么①和③并存**：③只在"向量层挂了"才整体生效；向量层正常但某轮语义没匹配上时不会触发③，关键信息照样漏。①是每轮必注入的保险丝，专治"检索偶尔没召回"。三层各管一种失效。

### 5.2 检索 query 构成

**query = 当前消息 + 最近 1~2 轮对话**。理由：用户说"继续""好"这类短消息时语义几乎为零，纯当前句召回全靠运气。从 history 尾部取最近 2 条拼接。

**边界规则：query 无文本时跳过②**。纯图片消息（promptText 为空/极短且无 OCR 文本）不构造向量 query——无意义的 embedding 调用只会产生噪声召回，直接走 ①+③。

### 5.3 合并与预算

- 三路结果按记忆 id 去重合并（①优先级最高，②次之，③补位）；
- **Token 预算固定，条数不固定**（企业级通行做法）：注入总量约 1000 token 封顶，超预算时按 ①→②→③ 顺序保留、同层内按相关性/重要性截断；
- 问题简单时召回条数自然少（省 token、少干扰），复杂时多注入。

### 5.4 降级的三个魔鬼细节

1. **吵闹降级，不沉默**：兜底触发时记 `warn` 日志（module: MemoryService，含失败原因），Loki 可直接观测。降级对用户透明，对维护者显眼——否则向量库坏了三个月没人发现，大家天天"爬楼梯"还以为电梯拆了；
2. **超时是真正的触发器**：向量库故障最常见形态是吊着不响应而非抛错。检索包 2~3 秒超时（记忆库几百条，正常几十毫秒），到点即放弃落③——否则"降级成功"了但每轮多等几秒，体验已坏；
3. **区分真空与假空**：检索空结果有两种——用户确实没有相关记忆（正常）；collection 被删/重建失败（异常）。判定：**用户在 MySQL 有记忆但向量库查不到任何向量 = 异常信号** → 落③ + warn + 异步触发该用户全量重建（自愈，见第 8 节）。

### 5.5 开关与回滚

`MEMORY_VECTOR_ENABLED=false`（或运行期异常）→ 完整回到现状 top-20 行为。**回滚 = 关开关，零风险。**

## 6. 写路径：CRUD 写穿同步

### 6.1 原则

> 目录跟着账本走：MySQL 先落库（真相优先），向量库同步失败不回滚 MySQL——账本是对的，目录错得起，事后可补抄。

### 6.2 CRUD 映射表

| 用户操作 | MySQL（真相） | 向量库（目录） |
|---|---|---|
| 新增（手动/自动提取/合并出新） | 插入行拿 id | embed → `mem_{id}` 写入 |
| 编辑内容 | 更新该行 | 重新 embed，同 ID 覆盖 |
| 仅编辑属性（类别/重要性） | 更新字段 | 按 ID 更新 metadata，不重新 embed（见 4.4） |
| 删除 | 删除该行 | 按 `mem_{id}` 精确删除 |
| 清空 | 删该用户全部行 | 按 `where userId` 批量删除 |

### 6.3 收口

所有写路径（`addUserMemory`、`updateUserMemory`、`deleteUserMemory`、`clearUserMemories`、提取器 `checkAndExtractMemories` 的 new/update 分支）**收口到同一个写穿辅助函数**。收口的意义：以后新增任何写记忆入口，天然不会漏同步——散落各处写迟早漂移。

### 6.4 同步失败处理

- 记 error 日志（module、memoryId、原因）；
- MySQL 记忆行打"待同步"标记（见第 7 节，UI 据此显示徽标）；
- 不重试阻塞主流程；自愈兜底交给全量重建。

## 7. 用户自定义记忆与同步状态（弹框问题的方案修正）

### 7.1 原提案

检索先查向量库、查不到再查数据库，并弹框询问用户"是否上传此记忆到向量库"；记忆模块提供上传按钮（全量/单个）。

### 7.2 采纳的部分

- ✅ **检索兜底**：向量库没有 → 数据库层 LIKE 关键词检索 → 仍能召回（即 5.1 的③层，且 LIKE 比 top-20 对"邮箱"这类具体词召回更准）；
- ✅ **上传按钮（全量/单个）**：记忆模块必备运维能力；
- ✅ **一条记忆一个 chunk**：与 4.2 文档模型一致。

### 7.3 修正的部分：聊天时不弹框，改"状态徽标 + 一键补传"

**为什么不在聊天中弹框**：

1. **写穿使"库有向量无"从常态变异常态**——正常情况下用户根本不需要做任何"上传"动作，弹框出现的场景本身就不该发生；
2. **打断对话的 UX 事故**：用户正在问"把图表发我邮箱"，聊天窗弹出"是否将记忆上传到向量库？"——用户既不理解也不关心基础设施细节，这是把运维问题甩给用户的反模式；
3. **时机错位**：检索发生在回答生成前的一瞬间，弹框阻塞会拖慢每轮响应。

**替代设计（保留用户控制权，不侵入聊天）**：

| 机制 | 说明 |
|---|---|
| 同步状态徽标 | 记忆列表每条显示"已同步 / 待同步"（依据 6.4 的标记），用户对状态有完全感知 |
| 一键补传 | "待同步"条目旁提供单个补传按钮；列表头部提供"全部同步"按钮 |
| Banner 提示 | 存在待同步条目时，记忆模块顶部显示非阻塞提示条（"N 条记忆待同步到向量库 [立即同步]"） |
| 聊天内兜底 | 即使不点同步，③层 LIKE 兜底保证 AI 仍能检索到该记忆——**同步状态不影响智能，只影响最优检索质量** |

一句话：**聊天里 AI 永远能找到记忆（兜底），记忆模块里用户永远看得见状态（徽标）——两个场景各用各的交互，不互相打扰。**

### 7.4 术语澄清

按钮命名统一为"**同步到向量库**"，不用"上传到知识库"——记忆不进知识库 collection（见 4.1），混用词会误导后续维护者。

## 8. 全量重建（对账 / 迁移 / 自愈三合一）

一个动作三种用途：

1. **存量迁移**：上线时把现有 20+ 条历史记忆灌入向量库（改造的必经步骤）；
2. **手动对账**：管理员/用户发现状态异常时，一键重建该用户全部向量；
3. **自动自愈**：5.4-3 检测到"假空"时异步触发。

实现：读该用户 MySQL 全部记忆 → 逐条 embed → 写入 `user_memories` collection（先清该用户旧向量再写，幂等）。几百条规模耗时秒级。前端触发入口即 7.3 的"全部同步"按钮。

## 9. 配置项（zod 化，同步 .env.example）

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `MEMORY_VECTOR_ENABLED` | `true` | 总开关；false 时完全回到 top-20 现状（= 回滚开关） |
| `MEMORY_VECTOR_TIMEOUT_MS` | `3000` | 单次向量检索超时，到点落兜底层 |
| `MEMORY_RETRIEVAL_TOP_K` | `8` | 检索层召回条数 |
| `MEMORY_CORE_LAYER_LIMIT` | `10` | 核心层（importance=5）注入上限 |
| `MEMORY_INJECT_TOKEN_BUDGET` | `1000` | 注入总 token 预算（粗估：字符数/1.5） |

约束：新增配置必须加入 `fundamentals/config.ts` 的 zod schema（fail-fast），同步 `.env.production.example` 附中文说明——上轮 `OUTPUT_REVIEW_TIMEOUT_MS` 缺模板项的教训不重演。

## 11. 测试计划

| 用例组 | 覆盖点 |
|---|---|
| 写穿同步 | 增/改/删/清空后向量库状态一致；同步失败产生"待同步"标记且 MySQL 不回滚 |
| 编辑分档 | 改内容触发 re-embed 且检索命中新内容；仅改类别/重要性不触发 re-embed、metadata 同步更新 |
| 类别治理 | 同义词提议归并入现有类不新建；通过守护的新类别 DISTINCT 可见；向量 metadata 与 MySQL 类别一致 |
| 边界输入 | 纯图片/空文本消息跳过②层不调 embedding；注入后 accessCount 仍正常递增 |
| 三级瀑布 | ①永远在注入中；②正常召回含第 21 条记忆；②超时/异常落③；③LIKE 命中"邮箱"类具体词 |
| 去重与预算 | 三路合并按 id 去重；超预算按 ①→②→③ 截断 |
| 隔离 | 用户 A 检索结果绝不含用户 B 的记忆；知识库内容不混入 |
| 真假空 | MySQL 有记忆 + 向量库空 → 触发自愈重建；真无记忆 → 正常空结果 |
| 开关回滚 | `MEMORY_VECTOR_ENABLED=false` 行为与现状逐字节一致 |
| 存量迁移 | 重建后向量计数 = MySQL 记忆数；重复执行幂等 |

## 12. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 向量库故障拖慢响应 | 3 秒超时硬上限，落③继续 |
| 同步 bug 造成脏索引 | MySQL 真相 + 全量重建兜底，秒级修复 |
| 检索质量回归（召回噪声） | top-8 限量 + Token 预算 + 核心层保底；最差情况=③层现状 |
| 上线引入不可用 | 开关回滚 = 回到现状，零风险 |
| 多用户串扰事故 | userId 强制过滤 + 测试用例钉死（11 节隔离组） |
| 自动提取是异步的：新记忆落库后、embed 写入前的窗口期，下一轮②层可能未收录 | ③层关键词兜底能按具体词召回；importance=5 的进①层。窗口期秒级，可接受 |
| 提取合并（异步）与用户编辑/删除并发，写回可能覆盖或落空 | mergeActions 写回按 existingMemoryIndex 定位，记录已删则 TypeORM update 空匹配为幂等 no-op；不阻塞不报错，用户侧操作优先 |
| 注入链路改造遗漏 accessCount 递增 | 三级瀑布重构必须保留递增逻辑（供后续衰减/统计），列入 11 节测试 |

## 13. 设计原则速记（评审用）

1. 真相源唯一：MySQL 是账本，向量库是目录，目录可随时重抄；
2. 任何时刻不差于现状：三级瀑布 + 开关回滚，改造即降级链；
3. 同步是确定的：确定性 ID + 写穿收口，搜索式删除不做；
4. 降级要吵闹：fail-open 但 warn 日志必须留痕；
5. 控制权给用户、打扰不给用户：聊天内兜底静默，记忆模块内徽标可见。
